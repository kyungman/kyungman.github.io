Xcode 업데이트 대응을 마치고 iPhone Duo 시뮬레이터에서 앱을 실행했다. 처음에는 화면이 넓어진 만큼 레이아웃을 조금 조정하면 될 거라고 생각했다.

그런데 하단 탭바가 보이지 않았다. 상단에 있던 테마 전환 버튼도 사라진 것처럼 보였다. 가로로 돌리면 화면 아래에 회색 띠가 생겼고, 상세 화면에서는 뒤로가기 버튼이 익숙하지 않은 위치에 나타났다.

한 화면을 수정하고 다음 화면으로 넘어가면 비슷하면서도 다른 문제가 나왔다. 공유 화면은 오른쪽이 비었고, PIN 입력 화면은 숫자 키패드만 왼쪽으로 쏠렸다.

작업을 이어가면서 반복해서 확인한 것은 화면 크기보다 **뷰가 어느 영역을 기준으로 배치되는가**였다.

## 탭바가 사라진 줄 알았는데 옆으로 이동하고 있었다

기존 앱은 커스텀 탭바를 사용하고 있었다. 시스템 탭바의 기본 표현을 숨기고, 별도의 버튼과 배경을 배치하는 구조였다.

이 구현에는 하단에 가로 탭바가 있다는 전제가 들어 있었다. Duo에서 시스템이 탭을 세로로 배치하자, 기존 커스텀 처리와 충돌했다.

Apple도 Duo의 탭과 네비게이션이 기기 상태에 따라 세로로 배치될 수 있다고 안내한다. 화면을 회전했을 때 하단 탭바가 그대로 남는다고 가정할 수 없었다. [Apple의 Duo 앱 준비 안내](https://developer.apple.com/videos/play/tech-talks/111461/)

대응은 배치 상태에 따라 나눴다.

- 가로 탭바에서는 기존 커스텀 표현을 유지했다.
- 세로 탭바가 활성화되면 커스텀 탭바를 제거하고 시스템 배치를 사용했다.

현재 배치 상태는 `verticalBarEdge`로 확인했다. 변경도 관찰해서 기기 상태가 달라지면 탭바를 다시 배치하도록 했다. 관련 API는 [UIKit 업데이트 문서](https://developer.apple.com/documentation/updates/uikit)에 정리돼 있다.

세로 화면과 가로 화면에서 선택된 아이콘 색상이 달랐던 문제도 여기서 발견했다. 커스텀 탭바에 지정한 색상과 시스템 컨트롤이 상속받는 `tintColor`를 맞춰 두 표현을 통일했다.

## 회색 띠를 따라가니 콘텐츠 높이 계산이 나왔다

가로 화면 아래에 회색 공간이 보였다. 처음에는 배경색 문제처럼 보였지만, 다크 모드에서도 같은 위치에 나타났다.

동시에 상단 배너도 보이지 않았다. 색상만 바꾸기 전에 헤더와 테이블이 실제로 차지하는 영역부터 확인해야 했다.

기존 레이아웃에는 상태 표시줄, 네비게이션바, 탭바의 높이를 조합해 콘텐츠 높이를 계산하는 코드가 있었다. 상하단에 바가 놓이는 화면에서는 맞았지만, 컨트롤이 옆으로 이동한 상태에서는 같은 계산을 적용하기 어려웠다.

상세 화면에서는 커스텀 헤더와 탭을 Safe Area의 위치와 너비에 맞춰 배치했다. 자식 화면의 프레임을 설정할 때는 부모 화면에서 계산한 좌표를 실제 컨테이너의 좌표로 변환했다.

```swift
childView.frame = view.convert(childFrame, to: container)
```

다만 모든 뷰를 Safe Area 안으로 줄이지는 않았다. 상세 화면의 테이블처럼 아래까지 이어져야 하는 콘텐츠는 화면 하단까지 확장했다. 버튼이나 검색창이 놓이는 영역과, 스크롤 콘텐츠가 채우는 영역을 따로 판단했다.

높이가 없는 하단 컨테이너에 남아 있던 그림자도 함께 정리했다. 컨테이너 크기가 바뀔 때 그림자 경로를 갱신하고, 영역이 비어 있으면 그림자를 숨겼다.

## 검색창은 남고 배너만 사라져야 했다

목록 화면에는 검색창과 배너가 있었다. 스크롤할 때 배너는 사라져도 검색은 계속 사용할 수 있어야 했다.

그런데 Duo 가로 화면에서는 네비게이션바 축소 동작까지 겹쳤다. 원래 의도했던 스크롤 동작과 시스템의 바 축소가 동시에 화면에 영향을 주고 있었다.

이 화면에서는 네비게이션바를 유지하도록 설정했다.

```swift
if #available(iOS 27.0, *) {
	navigationItem.navigationBarMinimization
		.minimizationBehavior = .never
}
```

다른 목록 탭에서도 같은 증상이 있어, 필요한 화면에 같은 정책을 적용했다. 네비게이션바의 스크롤 축소 동작은 [`UIBarMinimization`](https://developer.apple.com/documentation/uikit/uibarminimization-c.class)으로 제어할 수 있다.

배너 이미지의 표현도 별도로 결정했다. 이미지 전체를 보여주는 `scaleAspectFit`을 적용하면 넓은 화면에서 여백이 생겼다. 최종적으로 영역을 꽉 채우는 방향을 선택해 `scaleAspectFill`과 클리핑을 적용했다. 이 경우 이미지 일부가 잘릴 수 있다는 차이를 함께 고려했다.

## 상세 화면에서는 뒤로가기 버튼을 상단에 남겼다

메인 탭에서는 시스템의 세로 배치를 사용했지만, 모든 화면에 같은 방식을 적용하지는 않았다.

상세 화면에는 제목 아래에 여러 콘텐츠 탭이 있었다. 네비게이션까지 옆으로 이동하자 기존 구성과 어색하게 맞물렸고, 뒤로가기 버튼도 찾기 어려워졌다.

이 화면은 상단 네비게이션을 유지하기로 했다.

```swift
@available(iOS 27.1, *)
override var preferredVerticalBarBehavior: UIVerticalBarBehavior {
	.disabled
}

@available(iOS 27.1, *)
override var childForPreferredVerticalBarBehavior: UIViewController? {
	nil
}
```

일부 설정 화면도 같은 방식으로 맞췄다. 메인 화면과 상세 화면의 역할이 다르므로 네비게이션 배치도 화면별로 결정했다.

옆에 남는 배경색은 상단 네비게이션과 같은 색으로 맞췄다. 테이블이 사이드 컨트롤 영역까지 침범하는 부분에는 좌우 Safe Area를 반영했다.

## 공유 화면과 PIN 키패드는 서로 다른 기준으로 정렬돼 있었다

공유 화면은 오른쪽에 빈 공간이 생겼다. 확인해 보니 해당 패널을 감싸는 제약에 Duo의 오른쪽 Safe Area가 반영되고 있었다. 이 패널은 전체 영역을 사용하도록 조정했다.

PIN 화면은 조금 달랐다. 패널 위치를 맞춘 뒤에도 숫자 키패드만 왼쪽으로 쏠려 있었다.

화면을 감싼 패널과 키패드가 같은 중심을 기준으로 배치되지 않았기 때문이다. 키패드 중심을 무조건 화면 중앙으로 옮기는 대신, 기준 패널의 중심을 키패드 부모 뷰의 좌표로 변환했다.

```swift
let centerX = referenceView.convert(
	CGPoint(x: referenceView.bounds.midX, y: 0),
	to: parent
).x

pad.center.x = centerX
```

실제 구현에는 이동한 키패드가 부모 영역을 벗어나지 않는지도 확인하는 조건을 넣었다.

키패드를 닫는 과정에서는 별도의 배열 범위 예외도 발생했다.

```text
NSRangeException
index 5 beyond bounds [0 .. 4]
```

이 문제에는 키패드 SDK가 윈도 제스처 지연 설정을 변경하는 옵션을 Duo에서 끄는 방식으로 대응했다. 위치 수정과 충돌 대응은 별개의 변경이었다.

SDK 내부에서 해당 인덱스에 접근한 원인까지 확인한 것은 아니므로, 이 옵션을 모든 기기에 적용하지는 않았다.

## 팝업을 띄운 채 뒤로가면 부모 화면에 남았다

상세 화면에서 필터나 설정 패널을 띄운 뒤, 사이드의 뒤로가기 버튼으로 이동하면 화면이 이상하게 남는 문제도 있었다.

팝업은 네비게이션 컨트롤러의 뷰에 추가돼 있었다. 상세 화면에서 벗어나도 팝업이 부모 뷰에 붙어 있을 수 있는 구조였다.

화면이 사라질 때 관련 오버레이를 제거하도록 했다. 필터를 적용하지 않고 나가는 경우에는 임시 선택 상태도 되돌렸다.

팝업 애니메이션의 위치 계산도 바꿨다. 전체 디스플레이 높이인 `UIScreen.main.bounds.height` 대신, 팝업이 실제로 올라간 컨테이너의 `bounds`를 사용했다.

넓은 화면이나 크기가 달라지는 환경에서는 디스플레이와 현재 화면 컨테이너를 같은 것으로 보면 안 됐다.

## 웹뷰 문제인 줄 알았는데 네비게이션 제목이 비어 있었다

웹 화면에서는 가로 상태의 네비게이션바가 얇은 띠처럼 보였다. 웹뷰 상단도 가려져 보여 처음에는 웹뷰의 위치나 배경을 의심했다.

하지만 웹뷰를 위로 옮기는 것으로 해결할 문제는 아니었다. 이 사례에서는 네비게이션 제목을 명시한 뒤 상단 바가 정상적으로 표시됐다.

이 과정에서 넣었던 배경 우회 처리는 제거했다. 겉으로 같은 빈 공간처럼 보여도, 콘텐츠 제약 문제와 네비게이션 구성 문제는 따로 확인해야 했다.

## 일반 iPhone을 다시 확인해야 끝나는 작업이었다

Duo 전용 조건을 넣었다고 기존 iPhone에 영향이 없다고 말할 수는 없었다. 공통 탭바와 헤더 컨테이너를 수정한 부분도 있었기 때문이다.

작업 중에는 일반 iPhone 시뮬레이터에서도 주요 탭과 상세 화면, 웹 화면을 확인했다. PIN 화면은 Duo에서 위치와 동작을 확인했고, 이후 정상 동작한다는 사용자 확인도 받았다.

다만 모든 기기와 화면, 전환 조합을 검증한 것은 아니다. 실제로 확인한 흐름과 코드만 반영한 항목은 구분해 두어야 했다.

Duo 대응에서 반복해서 도움이 된 질문은 이것이었다.

> 지금 계산에 쓰는 크기와 좌표는 어느 뷰의 것인가?

화면 전체 너비인지, Safe Area 안쪽 너비인지, 자식 뷰가 들어간 컨테이너의 너비인지에 따라 결과가 달랐다. 키패드 중앙 정렬부터 팝업 애니메이션, 상세 화면의 하단 여백까지 같은 질문으로 다시 확인할 수 있었다.

작업 중 시뮬레이터 자체가 멈춘 일도 있었다. 그때는 코드 수정 없이 강제 종료와 재부팅으로 복구했다. 해당 과정은 [Duo 시뮬레이터 실행 문제를 복구한 기록](https://kyungman.github.io/posts/iphone-duo-simulator-launch-stuck/)에 따로 남겼다.
